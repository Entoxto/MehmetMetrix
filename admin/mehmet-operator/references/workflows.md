## Общий контракт

Использовать этот файл для повторяемых текстовых и голосовых команд над листом
`Поставки`. Доменные форматы и формулы брать из `docs/AI_CONTEXT.md` и
`docs/EXCEL_PIPELINE.md`; этот файл задаёт порядок операторских действий и
значения по умолчанию.

Для каждой команды:

1. Преобразовать разговорную формулировку в объект, действие и набор полей.
2. Разрешить относительные даты в часовом поясе `Europe/Moscow` и назвать
   получившуюся календарную дату в отчёте.
3. Найти ровно одну целевую поставку и позицию. Использовать год, номер
   поставки, наименование, цвет и соседние строки. Если остаётся несколько
   равноправных вариантов, запросить уточнение до записи.
4. Перед записью прочитать весь затрагиваемый блок поставки и соседние строки:
   значения, формулы, объединения, проверки данных, заметки, границы и
   форматирование.
5. Различать вводимые и вычисляемые поля. Не заменять ручными значениями формулы
   G, I, K, L, N, O и Q.
6. Выполнить минимальное изменение и повторно прочитать исходный и целевой
   блоки. Проверить значения, формулы, итоги и границы поставок.
7. Не создавать отдельную локальную резервную копию XLSX. Google Sheets
   остаётся рабочим черновиком с собственной историей версий; Git хранит
   историю кода, правил и фотографий. Каноническая публикация может скачать
   актуальный XLSX как служебный вход конвейера, но не как отдельную точку
   отката.
8. Сообщить, что было указано пользователем, что выведено по умолчанию и какие
   данные остались неизвестны. После завершённого набора изменений предложить
   отдельно опубликовать данные приложения.

## Оформление границ поставки

После любой операции, которая добавляет, удаляет, переносит или переставляет
строки, сохранять визуальную структуру блока поставки:

- верхняя и нижняя горизонтальные границы поставки по всей ширине рабочего
  диапазона остаются жирными;
- горизонтальные границы между позициями одной поставки остаются тонкими;
- прежнюю нижнюю границу при расширении блока делать внутренней тонкой, а
  жирную нижнюю границу переносить на новую последнюю строку;
- при сокращении или переносе строк восстанавливать жирные внешние и тонкие
  внутренние границы и в исходной, и в целевой поставке;
- разделитель года сохраняет собственное оформление и не используется как
  шаблон обычной строки поставки;
- вертикальные границы и остальные параметры оформления брать из соседнего
  корректного блока; не утолщать рамку каждой отдельной ячейки.

Перед записью прочитать границы полного затрагиваемого блока и соседней
корректной поставки. После записи повторно прочитать форматирование всех строк
исходного и целевого блоков и убедиться, что жирные линии отмечают только
внешние границы поставок.

## Значения по умолчанию

| Ситуация | Действие |
| --- | --- |
| Новая строка заказа | Записать в B текущую дату действия как настоящую дату Google Sheets в формате `dd.MM.yyyy` |
| Несколько позиций в одной команде | Считать одним размещением заказа и использовать одну дату B, если пользователь не разделил их на разные заказы |
| Новая позиция | Записать в E `В производстве 🛠️`; разговорное «в работе» для позиции означает это допустимое значение списка |
| Новая поставка | Записать в F первой строки `В работе 🧵`; E каждой позиции всё равно получает свой статус |
| Позиция в существующей поставке | Не менять F и не создавать второй статус поставки |
| Повторная позиция без цены | Взять H из ближайшей предыдущей строки с тем же очищенным наименованием C |
| Явно названная цена | Использовать её только для новой строки; историю не переписывать |
| Цена не названа и совпадения нет | Оставить H пустой, не угадывать и сообщить, что цена требует уточнения |
| Повторная позиция без состава | Копировать D из предыдущей строки с тем же очищенным наименованием |
| Новая модель с очевидным фактическим материалом | Если материал прямо и однозначно назван в C, вывести первую строку D из него и использовать подтверждённый шаблон подкладки для этой категории; например, `из меха кенгуру` → `100% Натуральный мех кенгуру` + стандартная подкладка |
| Состав неоднозначен или название описывает внешний вид | Не угадывать D: учитывать подтверждённые исключения C ↔ D и запросить уточнение для новой неоднозначной комбинации |
| Карго названо, курс ещё неизвестен | Записать сумму в M; не заполнять N, O или Q вручную — формулы оставят их пустыми до появления положительного курса J |
| Новая поставка без номера | Использовать следующий номер текущего года; нумерация каждого года начинается заново |
| Не названо место вставки внутри поставки | Добавить позицию в конец её блока перед жирной нижней границей |

Очищенное наименование — полная строка C без последних скобок размеров или
`(N шт.)`, с нормализованными пробелами. Цвет остаётся частью совпадения.

## Добавление позиции

Минимально нужны изделие и размеры либо общее количество. Поставка может быть
названа явно или однозначно следовать из контекста. Если в таблице несколько
подходящих активных поставок, не выбирать одну только по принципу «самая
последняя».

### В существующую поставку

1. Определить конец блока поставки по A и разделителям года.
2. Вставить строку перед нижней границей либо использовать подготовленную
   пустую строку только после проверки, что она не принадлежит другому блоку.
3. Заполнить B, C, D, E и H по значениям пользователя и правилам по умолчанию.
4. Оставить A и F пустыми в строке продолжения поставки. Не переносить в неё
   значения J, M, P или Q без отдельного смысла.
5. Восстановить проверки данных, заметки, форматы и построчные формулы
   G/I/K/L/N/O по корректному соседнему образцу с новыми ссылками на строку.
6. Перенести жирную нижнюю границу поставки на новую последнюю строку; внутренние
   границы оставить тонкими.
7. Проверить G, I, K, L, N, O и контрольный итог Q поставки.

### Как новая поставка

Дополнительно создать следующий номер A текущего года, установить F
`В работе 🧵` и поставить формулу Q в первую строку поставки. Не копировать
курс J, карго M, дату/ETA P или финансовые значения из предыдущей поставки.

Если одной командой добавлено несколько позиций, они образуют один новый блок:
номер поставки, её статус и Q принадлежат первой строке или объединённым ячейкам,
а построчные значения и формулы остаются отдельными.

## Перенос позиции

Перенос не является новым размещением заказа. Сохранять исходную дату B, C, D,
E, H и относящиеся только к позиции заметки, если пользователь не попросил их
изменить.

Не переносить вслепую поля уровня поставки и финансового блока: A, F, J, M, P
и Q. После переноса позиция рассчитывается в контексте целевой поставки.

Порядок действий:

1. Прочитать целиком исходную и целевую поставки.
2. Проверить, к какому блоку курса J и карго M относится позиция.
3. Если перенос меняет распределение общего карго либо его нельзя однозначно
   вывести, запросить решение до записи.
4. Переместить позиционные значения, восстановить формулы с новыми номерами
   строк и применить проверки/оформление целевого блока.
5. Пересобрать объединения и жирные внешние границы обеих поставок.
6. Проверить Q и финансовые итоги обеих поставок; явно сообщить об изменившихся
   суммах.

Если переносится единственная позиция исходной поставки, отдельно подтвердить
удаление ставшего пустым номера поставки: такая операция меняет историю, а не
только порядок строк.

## Изменение размеров или количества

Менять исходное представление в C, сохраняя G формульной:

- известные размеры: `(XS-2, S-3, M-1)`;
- известно только общее количество: `(10 шт.)`;
- нет размеров и количества: позиция означает одну вещь.

Не смешивать размеры с `(N шт.)`, не повторять размер и не использовать
нулевые, отрицательные или дробные количества. При `(N шт.)` приложение должно
показывать «Размеры на уточнении»; это не статус E.

После изменения сверить G с C и проверить пересчёт I, L, N, O и Q. Не менять
H, если пользователь изменил только размерный состав.

### Маркер «Под вопросом»

Когда возможность выпуска позиции ещё не подтверждена, записывать
`под вопросом` в последние скобки C. Маркер независим от статуса E, образца и
размеров, поэтому допустимы формы `(под вопросом)`,
`(образец XS-1, под вопросом)` и `(10 шт., под вопросом)`. Не менять из-за него
E, G, H или финансовые формулы. После записи проверить, что G сохранила прежнее
количество, а парсер создаёт `underQuestion: true`.

## Чтение и точечное изменение

Запросы «покажи», «сколько», «какой статус», «когда ожидается» и подобные по
умолчанию являются только чтением. Ответ связывать с годом, номером поставки,
позицией и строкой таблицы, чтобы совпадение можно было проверить.

Команды «измени», «поставь», «перенеси», «добавь» и «исправь» разрешают запись
только в названный объект. Разговорное название поля сопоставлять с колонкой по
`docs/EXCEL_PIPELINE.md`; соседние формулы и оформление можно корректировать
лишь как обязательную зависимость операции.

Для статусов использовать актуальную строгую проверку данных из таблицы.
Различать статус позиции E и статус поставки F; не записывать значение из
списка F в E и наоборот.

## Дата поступления и ETA

Колонка P принимает два разных значения:

- настоящую дату — продукция фактически получена;
- текст — ожидаемый срок, который приложение показывает как ETA.

Относительные формулировки разрешать так:

- `в четверг` — ближайший четверг, который не раньше даты команды;
- `в следующий четверг` — четверг следующей календарной недели;
- `через неделю` — дата команды плюс семь календарных дней;
- `перенеси на следующую неделю` — текущая распознанная дата ETA плюс семь
  дней; если даты в ETA нет, запросить основу расчёта.

Если пользователь не задал точный текст, записывать единообразно:
`Доставка ожидается в четверг, 20.08`. Для даты не текущего года добавлять год.
Если пользователь продиктовал готовую формулировку, сохранять её смысл и тон.

При обновлении прогноза заменять существующий текст ETA, а не добавлять второй:
парсер выбирает первый текст поставки. При фиксации фактического получения
удалить устаревший текст ETA этой поставки и записать настоящую дату. Не
заменять уже зафиксированную дату получения прогнозом без явного указания, что
это исправление.

Служебные объединения блока поставки восстанавливать скриптом
`scripts/merge_cells.py --year <год> --shipment <номер>`:

- A (номер поставки), P (дата поступления / ETA) и Q (всего оплачено) — по всему
  блоку поставки;
- J (курс) — по всему блоку только если курс заполнен; пустую J не объединять;
- F (статус поставки) — только для `В пути 🚚`, `Получено, не оплачено 📦` или
  `Получено, оплачено ✅`; для `В производстве 🛠️` и `В работе 🧵` F оставлять
  построчным, без объединения.

Перед переносом или перестройкой строк сначала выполнить
`scripts/merge_cells.py --year <год> --shipment <номер> --mode unmerge`, затем
изменить строки и после этого снова выполнить режим `merge`. После каждой
операции проверять metadata листа `Поставки`: в `merges` должны быть диапазоны
с нужными `startColumnIndex`/`endColumnIndex` на весь актуальный блок, а не
только успешный exit-code скрипта.

## Синхронизация приложения

Использовать модель «черновик → явная публикация»:

- Google Sheets является рабочим черновиком;
- приложение читает последнюю успешно опубликованную версию;
- обычные изменения таблицы не запускают синхронизацию, сборку или деплой;
- не использовать Google-триггеры или периодический опрос как базовый способ
  публикации.

После завершённой команды или связанного набора команд:

1. Проверить изменённые диапазоны и кратко перечислить результат.
2. Если пользователь не сообщил, что продолжает редактирование, спросить:
   `Обновить данные приложения сейчас?`
3. Ответ `да` считать подтверждением только для непосредственно предложенной
   публикации. Не переносить старое подтверждение на последующие изменения.
4. Ответ `нет`, `позже` или продолжение редактирования оставляет изменения
   только в Google Sheets. Поздняя команда `обнови данные приложения`
   публикует всё актуальное состояние таблицы, а не только последнюю правку.

При подтверждённой публикации:

1. Заново прочитать или скачать полное актуальное состояние Google Sheets в
   момент запуска, чтобы не опубликовать устаревший снимок.
2. Выполнить `npm run publish:data`: единый конвейер Google Sheet → XLSX →
   snapshot в памяти + ручной `money.json` → проверки → защищённый publish API.
3. Ошибка до отправки сохраняет прежний пакет. После обрыва POST commit уже
   мог произойти: проверить version/hash и следовать диагностике скрипта,
   не объявляя прежнюю версию активной без проверки.
4. При успехе атомарно заменить опубликованный пакет данных и проверить
   `/api/data-version`; runtime читает пакет без кэша, поэтому отдельный сброс
   не требуется.
5. Сообщить опубликованную версию, результат проверок и оставшиеся
   предупреждения.

Публикация включает полный snapshot и ручной `data/money.json`, но не читает и
не меняет лист Google Sheets «Оплаты». Команда `npm run publish:data:dry-run`
разрешена для диагностики без подтверждения, поскольку не скачивает таблицу и
не запускает Python, не читает настройки публикации и не пишет файлы.

Локальная принудительная синхронизация и команда удалённого агента должны
вызывать один и тот же канонический publish-процесс. Windows batch
является только тонкой точкой входа в него, а не отдельной реализацией логики.

Git push и новый деплой нужны для изменений кода, агентских правил и пока ещё
репозиторных фотографий, но не для публикации обычных табличных данных.
Фотографии сначала должны попасть в действующий deploy: publish API отклоняет
пакет со ссылкой на отсутствующий в нём JPG.

## Развитие сценариев

После пользовательской коррекции:

1. Определить, является ли она общим правилом, исключением конкретной модели
   или разовой командой.
2. Общее операторское правило записать здесь.
3. Доменный инвариант дополнительно записать в его первичный источник из
   `project-map.md` и при необходимости закрепить тестом.
4. Разовое решение не превращать в глобальное правило.
5. Новый детерминированный инструмент добавлять в `scripts/` только когда
   сценарий стабилизирован на реальных примерах.
