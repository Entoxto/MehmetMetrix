# Mehmet Metrics

Внутренняя панель для контроля поставок изделий, финансовых обязательств и
каталога продукции.

Приложение решает три задачи:

1. показывает историю поставок и статусы позиций по годам;
2. считает суммы к оплате и учитывает ручные доплаты/депозиты;
3. предоставляет каталог с фото, ценами, размерами и материалами.

## Быстрый запуск

Проект закреплён на Node.js 24 через `.nvmrc` (минимум для текущего Next.js —
Node.js 20.9).

```bash
npm install
npm run dev
```

Приложение откроется на `http://localhost:3000`.

На Windows проект может использовать локальный Node.js из `.tools/node`:

```powershell
$env:PATH = "$PWD\.tools\node;$env:PATH"
```

Python-команды запускаются через `scripts/run_python.mjs`: сначала учитывается
`MEHMET_PYTHON`, затем `.venv` / локальный runtime / bundled Codex Python и
только после этого системный Python. Для внешнего окружения установите
зависимости один раз: `python -m pip install -r requirements.txt`.

Также доступны пользовательские Windows-сценарии:

- `Запустить проект.bat` — fast preflight и dev server без обновления данных;
- `Запустить с обновлением.bat` — Google Sheet → Excel → JSON → WebP → проверки
  → dev server;
- `Опубликовать данные.bat` — после подтверждения скачать свежую таблицу,
  проверить её и обновить данные работающего приложения без пересборки;
- `Собрать проект.bat` — полный preflight и production build.

Оба сценария запуска проверяют `http://localhost:3000` перед открытием браузера.
Если старый dev server этого проекта занял порт, но перестал отдавать готовую
страницу, `scripts/windows/start_dev_server.ps1` безопасно перезапускает только
процесс Mehmet Metrics. Чужой процесс на том же порту не завершается
автоматически и выводится как явная ошибка.

## Архитектура

```text
Excel / Google Sheet
        ↓
Python parser + validation
        ↓
data/*.json
        ↓
explicit publish → Netlify Blobs (`current` + version history)
        ↓
lib/dataSource.ts + lib/* + types/*
        ↓
app/*/page.tsx
        ↓
components/<area>/*
```

Маршруты остаются тонкими. Экранная разметка находится в соответствующей
предметной папке `components/`, а бизнес-правила — в `lib/`.

В TypeScript используется единый термин `Shipment`:

```typescript
interface Shipment extends ShipmentConfig {
  positions: Position[];
  totalAmount: number;
  hasPriceGaps: boolean;
}
```

Вычисленные позиции доступны как `shipment.positions`; отдельной внутренней
сущности `Batch` нет. Query-параметр `batch` сохранён только как legacy-контракт
существующих deep links.

## Источник правды

Excel / Google Sheet — источник правды для:

- поставок и статусов;
- размеров и количества;
- материалов;
- исторических и актуальных цен.

Файлы `data/shipments.json`, `data/products.json`, `data/meta.json` генерируются
и будут перезаписаны следующим импортом. Они являются входом публикации и
резервным снимком последнего deploy, но production-приложение обычно читает
последнюю явно опубликованную версию из Netlify Blobs.

`data/product-id-registry.json` — технический источник стабильных `productId`.
Publisher получает его из последнего authoritative versioned bundle перед
парсингом и публикует атомарно вместе с данными; история удалённых моделей и
занятые ID сохраняются между машинами. Legacy bundle без поля поддерживается
только для чтения до первой новой публикации; новый POST без реестра запрещён.
Парсер работает с временной staging-копией, а tracked-файл заменяется лишь после
подтверждения публикации. Runtime UI от реестра не зависит.

`data/money.json` редактируется вручную:

- `deposits` — депозиты и предоплаты;
- `pendingManual` — дополнительные ручные строки к оплате.

Все четыре JSON и технический реестр входят в один атомарный публикуемый пакет. Лист Google Sheets
«Оплаты» в этот процесс не вовлечён.

Подробные правила: [`data/README.md`](data/README.md).

## Обновление данных

Локальная подготовка без изменения работающего приложения:

```bash
npm run data:fetch
npm run data:parse
npm run images:sync
npm run preflight:fast
```

Публикация по отдельному подтверждению:

```bash
npm run publish:data
```

Команда сама повторно скачивает полную таблицу, парсит и проверяет её, добавляет
ручной `money.json`, после чего атомарно переключает `current` в Netlify Blobs.
Если проверка или загрузка не удалась, предыдущая версия остаётся активной.
Настройка секрета, диагностика и контракт отката описаны в
[`docs/DATA_PUBLISHING.md`](docs/DATA_PUBLISHING.md).

Полный контракт парсера, используемые колонки и инварианты:
[`docs/EXCEL_PIPELINE.md`](docs/EXCEL_PIPELINE.md).

Ключевые правила:

- наименования следуют порядку `изделие + модель/крой/стиль + из материала — цвет`;
- общее количество без размерной сетки задаётся в C суффиксом `(10 шт.)`:
  формула G возвращает `10`, а приложение показывает «Размеры на уточнении»;
- независимый маркер неопределённости задаётся в тех же последних скобках C:
  `(образец XS-1, под вопросом)`, `(10 шт., под вопросом)` или
  `(под вопросом)`; приложение показывает плашку «Под вопросом», не меняя
  количество, статус и финансовую логику позиции;
- позиция без размеров и без явного количества считается одной вещью;
- для повторной позиции без явно названной цены в H используется цена её
  ближайшего предыдущего появления; явно указанная новая цена имеет приоритет;
- итог в I вычисляется автоматически как `G × H`, а при пустой или нулевой H
  остаётся пустым;
- себестоимость единицы в K использует курс J только внутри текущей поставки,
  а итог в L равен `K × G`; без известного положительного курса обе ячейки
  остаются пустыми, поэтому нулевые заглушки между поставками не нужны;
- сумма карго в M относится только к своему блоку внутри текущей поставки. N
  считает себестоимость единицы как `ROUND(K + M / сумма G блока)`, O — как
  `N × G`; одинаковые суммы карго в разных блоках не объединяются, а при
  неизвестном карго N и O остаются пустыми без нулевых заглушек в M. Карго
  можно записать заранее: пока положительный курс J неизвестен и K не
  рассчитана, N, O и итог поставки Q остаются пустыми;
- P принимает фактическую дату поступления либо свободный текст ожидаемого
  срока; приложение показывает их соответственно как дату или ETA;
- Q автоматически суммирует O внутри границ поставки из A и остаётся пустой,
  пока итоговая себестоимость не рассчитана;
- статусы сохраняются текстом из Excel 1:1;
- пустой статус позиции наследует статус поставки;
- `isPayable` определяет участие позиции в финансовых расчётах;
- Money отдельно показывает известную сумму и количество позиций/физических
  единиц без цены; полностью неизвестный долг не отображается как `$0`;
- неизвестные размеры и категории останавливают импорт;
- `sample` не принуждает количество к `1`;
- cost из колонки N используется только при положительном курсе в J;
- фото опционально, но заданный несуществующий путь является ошибкой.

## Изображения

```text
public/images/products/jpg/        оригинальные JPG/JPEG
public/images/products/webp/       полноразмерные WebP для страницы товара
public/images/products/webp/card/  облегчённые WebP для карточек и главной
```

Имя файла должно совпадать с названием модели. Если фото ещё нет, каталог
использует общий `__photo_pending`. Конвертер создаёт оба WebP-варианта и
пересобирает их после изменения исходного JPG. Карточный вариант автоматически
вписывает исходник целиком в квадрат и подбирает поля по углам фотографии:
вручную обрезать фото или дорисовывать фон не нужно.

На странице товара полноразмерное изображение также всегда вписывается целиком:
на desktop рамка принимает пропорции исходника, а на компактных экранах фото
занимает доступную ширину без `cover`-кропа.

Папка `jpg/` — единственный источник правды. Файлы в `webp/` и `webp/card/`
вручную редактировать или удалять не нужно:

1. добавьте, замените, переименуйте или удалите JPG/JPEG;
2. запустите «Запустить с обновлением» либо команду ниже;
3. конвертер создаст актуальные варианты и рекурсивно удалит лишние `.webp`, у
   которых больше нет исходника.

```bash
npm run images:sync
npm run validate:images
```

Если фото удалено без полного обновления данных, сначала запустите
`npm run data:parse`: старый `photo` в generated
`data/products.json` должен также исчезнуть.

Фотографии остаются статическими файлами и требуют Git push/deploy. Сервер
отклоняет пакет данных, если он ссылается на фото, которого ещё нет в текущем
deploy; сначала разворачиваются изображения, затем публикуются данные.

## Производительность

- корневое меню остаётся Static, а Work, Catalog, Money и карточки товаров
  рендерятся на сервере из последней опубликованной версии;
- route-компоненты читают пакет только на сервере, а клиент получает необходимые
  экрану props;
- `app/layout.tsx` не использует request-bound `headers()`/`cookies()`, чтобы не
  переводить весь проект в dynamic rendering;
- карточки используют уменьшенный вариант изображения, а детальная страница —
  полноразмерный;
- первая карточка главной и фото товара помечены как LCP-priority;
- тяжёлые таблицы Work монтируются только после раскрытия года и поставки.

Зафиксированные контракты, результаты контрольной сборки и порядок повторного
замера: [`docs/PERFORMANCE.md`](docs/PERFORMANCE.md).

## Навигация и UI

- `components/layout/AppShell.tsx` владеет общим каркасом;
- бренд `MM / Mehmet Metrics` всегда ведёт на `/`;
- кнопка «Назад» использует внутреннюю историю приложения;
- товар сохраняет источник перехода из Work или Catalog;
- состояние раскрытия Work живёт в `hooks/useWorkNavigationState.ts`;
- закрытая карточка поставки показывает весь состав и компактные метрики;
- состав интерпретирует последнюю часть названия после тире как цвет только в
  визуальном слое: на desktop это отдельная колонка, на mobile — вторая строка;
  исходное название из Excel не меняется;
- название позиции-образца использует тот же приглушённый фиолетовый акцент, что
  и плашка `Образец`; цвет изделия и количество сохраняют свои обычные роли;
- позиции с `underQuestion` получают отдельную плашку `Под вопросом` рядом с
  другими независимыми маркерами позиции;
- раскрытие поставки работает по всей поверхности карточки, кроме вложенных
  ссылок на товары и других интерактивных контролов; заголовок остаётся
  клавиатурным контролом с `aria-expanded`;
- тип поставки собирается из независимых плашек `Партия` и `Образец`: смешанная
  поставка показывает обе, без отдельной формулировки `С образцом`;
- на мобильном пара плашек переносится целиком и не разрывается между строками;
- повторяющиеся кликабельные карточки используют `ClickableCard`;
- экраны используют общий каркас `PageFrame` и вводный блок `PageIntro`;
- общие цвета, поверхности, типографика и motion-токены находятся в
  `constants/styles.ts`, а глобальные интерактивные состояния — в
  `app/globals.css`;
- типографика разделена по роли: `Lora` используется для заголовков и основного
  текста, `Manrope` — для сумм, метрик, таблиц и компактных контролов;
- числовые значения используют tabular numerals, поэтому суммы и колонки не
  «прыгают» при смене цифр;
- анимации обязаны учитывать `prefers-reduced-motion`.

## Проверка перед деплоем

```bash
npm run preflight
```

Команда запускает lint, обе TypeScript-проверки, TypeScript и Python-тесты,
валидацию данных/изображений и production build.

Проект развёрнут на Netlify. Код, правила и фотографии обновляются push в
deployment branch; обычные табличные данные и `money.json` — отдельной командой
`npm run publish:data` без сборки. Netlify запускает `npm run preflight` из
`netlify.toml`, поэтому deploy не продолжается при ошибке lint, типов, тестов,
валидации данных/изображений или production build.
