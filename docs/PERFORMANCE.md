# Производительность Mehmet Metrics

## Текущий контракт

Проект оптимизирован под небольшой, редко используемый внутренний набор данных.
Табличные JSON публикуются независимо от deploy, поэтому только корневое меню
предварительно собирается, а экраны данных рендерятся по запросу.

- `/` должен отображаться как `○ Static` в выводе `next build`.
- `/catalog`, `/money`, `/work` и `/product/[id]` должны отображаться как
  `ƒ Dynamic`: это осознанная цена обновления данных без rebuild.
- `lib/dataSource.ts` читает один пакет около 93 КБ из Netlify Blobs со строгой
  согласованностью. Текущая крайне низкая посещаемость не требует отдельного
  runtime-кэша; при росте трафика нужен замер перед его добавлением.
- `app/layout.tsx` не использует `headers()`, `cookies()` и другие request-bound
  API.
- Bundle loader и резервный generated JSON импортируют только серверные
  data-модули. Клиентские компоненты получают сериализованные props и не
  импортируют `data/*.json` или `@netlify/blobs`.
- Закрытые годы и поставки Work не монтируют внутренние таблицы.

## Изображения

Один исходный JPG имеет два производных варианта:

```text
jpg/<имя>.jpg        источник и последний fallback
webp/<имя>.webp      детальная страница товара
webp/card/<имя>.webp главная и карточки каталога
```

Карточный вариант ограничен размером `960 × 1200`, не увеличивает маленькие
исходники и сохраняется с quality 80. Полный вариант сохраняется с quality 85.
`scripts/convert_to_webp.py` пересобирает отсутствующий или изменённый вариант.
Он также рекурсивно удаляет `.webp`, которым больше не соответствует исходный
JPG/JPEG; другие расширения не затрагиваются.

Цепочка загрузки карточки:

```text
card WebP → full WebP → исходный JPG/JPEG → __photo_pending → 📷
```

Первая карточка главной и основное фото товара имеют `priority`; остальные
изображения остаются lazy.

## Контрольный замер

Текущий замер выполнен production-сборкой 13 августа 2026 года после перехода
на явную публикацию Netlify Blobs.

| Маршрут | Рендер | First Load JS |
| --- | --- | ---: |
| `/` | Static | 114 kB |
| `/catalog` | Dynamic | 112 kB |
| `/money` | Dynamic | 111 kB |
| `/product/[id]` | Dynamic | 112 kB |
| `/work` | Dynamic | 119 kB |

Набор из 60 полноразмерных WebP занимает 5,18 МиБ. Карточные варианты тех же
файлов занимают 2,12 МиБ — на 59% меньше; самый тяжёлый карточный файл —
128,3 КБ.

Эти числа — контрольная точка, а не жёсткий запрет на небольшие колебания после
обновления Next.js или данных. Важные регрессии: перевод корневого `/` в
Dynamic, попадание JSON/Blob SDK в client chunks и использование
полноразмерных фото в сетках.

## Как повторить проверку

1. Остановить dev server, чтобы он не удерживал `.next/trace`.
2. Запустить:

   ```bash
   npm run validate:images
   npm run build
   ```

3. Проверить, что `/` остался Static, четыре data-backed маршрута — Dynamic, а
   First Load JS не вырос без объяснимой причины.
4. После изменения исходных JPG выполнить:

   ```bash
   python scripts/convert_to_webp.py --auto
   npm run validate:images
   ```

   При удалении или переименовании JPG эта же команда очищает оба производных
   варианта. Если изменился сам набор фото каталога, перед ней нужно запустить
   Excel-парсер; стандартный сценарий «Запустить с обновлением» уже соблюдает
   этот порядок.

5. Перед деплоем запустить `npm run preflight`.

Виртуализация списков сейчас не нужна: текущий объём — 49 поставок и 131
позиций, а закрытые секции не монтируются. Вернуться к ней стоит, если один
раскрытый год начнёт содержать сотни одновременно отображаемых строк и
профилировщик покажет проблему рендера.
