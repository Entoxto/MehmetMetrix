# Явная публикация данных

## Модель и источники

Google Sheets — рабочий черновик. Сайт читает последний явно опубликованный
пакет из Netlify Blobs; таблицу runtime не опрашивает. Обычное обновление данных
не требует Git push или rebuild.

Пакет содержит `shipments`, `products`, `money`, `meta`, `productIdRegistry` и
поля `schemaVersion`, `version`, `publishedAt`, `sourceHash`. Все бизнес-поля и
реестр входят в SHA-256. `registryBaseVersion` существует только в POST-команде
как условие текущей версии; он не хранится в новом снимке и не входит в хеш.

Excel задаёт поставки и каталог, `data/money.json` — ручные финансы.
Авторитетный реестр ID берётся из активного Blobs-пакета. Лист «Оплаты»
конвейер не читает и не изменяет. Реестр сохраняет выданные ID исчезнувших
моделей; новые публикации не могут удалить записи или переиспользовать ID.

`data/snapshot.json` — единый tracked-снимок для локального запуска и резерва
сборки. Начальный файл при рефакторинге объединён из прежних generated-файлов
без изменения бизнес-данных; само объединение не является публикацией.
После подтверждённой публикации он целиком заменяется отправленным пакетом.
`tmp/preview-snapshot.json` — игнорируемый локальный черновик, только для
`next dev`. Production build и fallback Blobs его не используют.

## Каноническая команда

`npm run publish:data` после отдельного подтверждения пользователя:

1. Читает настройки и защищённый `GET /api/publish-data`: текущую версию и
   реестр. Ошибка GET, в том числе 404/405, останавливает процесс до импорта.
2. Скачивает свежую Google Sheet как XLSX в память. Python openpyxl читает
   только «Поставки», принимает реестр через stdin, возвращает JSON через stdout.
3. Node добавляет ручной `money.json`, вычисляет последние price/cost каталога,
   проверяет весь пакет общим `lib/dataBundle.ts` и локальные фото. Ни generated
   JSON, ни реестр, ни локальный XLSX на этом пути не перезаписываются.
4. Отправляет один кандидат с SHA-256, версией и `registryBaseVersion`.
5. API проверяет схему, хеш, соответствие каталога поставкам/реестру, историю
   ID, текущую версию и наличие каждого `photo` в действующем deployment.
   Текущий пакет и его ETag читаются вместе одной операцией.
6. API создаёт неизменяемую копию `versions/<version>`, затем атомарно заменяет
   `current` с условием ETag (или onlyIfNew при первом запуске).
7. CLI проверяет совпадение `version` **и** `sourceHash` через `/api/data-version`.
   Только после подтверждения атомарно заменяет весь `data/snapshot.json` и
   удаляет preview. Сброс runtime-кэша не нужен.

Повтор идентичного POST подтверждает уже активный пакет без записи либо
продолжает с точной архивной копии после сбоя до переключения `current`.
Если текущая версия уже продвинулась дальше, старый пакет получает 409 и не
перезаписывает её. Скрипт делает не более двух попыток с теми же байтами,
версией, хешем и base; повторного парсинга внутри retry нет.

## Что означает ошибка

| Момент | Удалённое состояние | Локальный snapshot |
| --- | --- | --- |
| GET, импорт, локальная валидация | Запись не начиналась | Прежний |
| API отклонил запрос до записи current (400/401/409/413) | Этот запрос current не изменил | Прежний |
| Архив создан, current ещё не записан | Прежний current, кандидат может остаться в versions | Прежний |
| Обрыв POST / storage 503 / недоступен data-version | Commit мог уже произойти | Прежний до подтверждения |
| Версия подтверждена, локальный rename не удался | Новый пакет активен | Скрипт явно предупреждает о локальном кэше |

Нельзя утверждать, что любая ошибка оставляет предыдущие данные активными.
После неопределённого ответа проверьте `/api/data-version` и сообщите фактическую
версию. 409 после повторной попытки также не отменяет возможный commit первой
попытки. При следующем отдельно разрешённом запуске publisher снова прочитает
активный реестр и свежую таблицу; локальный кэш не диктует production identity.

## Legacy и восстановление

Schema 1 и чтение архивных пакетов без реестра сохранены. Каждый новый POST
обязан содержать реестр. Нормальный CLI не берёт локальный seed, если на сервере
есть legacy current без реестра: требуется явная миграция из проверенной истории
ID. Для текущего проекта эта миграция уже выполнена. Seed из tracked snapshot
допустим для bootstrap только при `current.version === null`.

Архивы `versions/<version>` сохраняются. Откат данных — новая явно разрешённая
публикация: взять проверенные бизнес-поля нужного архива, сохранить **активный**
реестр с полной историей ID, проверить совместимость имён/ID и цен, создать
новые timestamp/hash/version и отправить через тот же API с текущим base.
Нельзя просто переустановить старый `current`: это могло бы потерять новые ID.
После отката проверить version/hash и заменить локальный snapshot.
Отдельного автоматического rollback-скрипта нет. Откат кода Netlify и откат
данных Blobs — разные операции; redeploy сам по себе `current` не меняет.

## Настройка и команды

Нужен Node.js 24+. Python launcher ищет `MEHMET_PYTHON`, локальный runtime,
bundled Codex Python, затем системный; для парсинга требуется openpyxl.
Внешние зависимости: `python -m pip install -r requirements.txt`.

В Netlify настроить секрет `MEHMET_PUBLISH_TOKEN`. На машине оператора создать
игнорируемый `.env.publish.local`:

```text
MEHMET_SITE_URL=https://eloquent-buttercream-3d732d.netlify.app
MEHMET_PUBLISH_TOKEN=<тот же секрет>
```

Переменные процесса имеют приоритет. Токен нельзя коммитить или выводить в лог.
На Windows POST использует PowerShell HTTP-клиент из-за наблюдавшихся разрывов
крупных Node POST: тело идёт через stdin, токен через окружение. Другие системы
используют встроенный fetch. `Опубликовать данные.bat` — только оболочка команды.

```bash
# Полностью офлайн: локальный snapshot/preview + текущий money + изображения.
# Не загружает таблицу, не запускает Python, не читает publish env, не пишет файлы.
npm run publish:data:dry-run

# Свежая таблица, полный пакет, явная запись и проверка результата.
npm run publish:data
```

Production: `eloquent-buttercream-3d732d`, deploy branch `main`, Netlify Project
ID `facb4a96-e9fc-4a07-951c-a49330c2e339`. Secret scanning включён; исключён
только приватный generated Turbopack cache `.netlify/.next/cache/**`.

## Runtime и фотографии

`lib/dataSource.ts` валидирует embedded snapshot и каждое прочитанное `current`.
На Netlify чтение strong и без request-кэша; повреждённый/отсутствующий пакет
или ошибка Blobs переключает чтение на snapshot последней сборки. `/` остаётся
Static, Work/Catalog/Money/Product рендерятся на сервере по запросу.

`MEHMET_DATA_SOURCE=local` выбирает локальные данные (preview только в dev);
`netlify-blobs` принудительно выбирает Blobs. `MEHMET_DATA_STORE` переопределяет
store `mehmet-metrics-data`. Для прямой локальной диагностики Blobs нужны
`NETLIFY_SITE_ID` и `NETLIFY_AUTH_TOKEN`; обычному publisher они не требуются.

Фото не входят в Blobs. Новые JPG/JPEG и производные WebP сначала должны попасть
в deployment: добавить фото → images:sync → preflight → разрешённый Git push →
успешный deploy → отдельно разрешённый publish:data. Проверка изображений
проверяет и build fallback, и имеющийся preview. При удалении фото учитывайте
также ссылки активного пакета: сначала уберите ссылку из источника/публикации,
а затем удаляйте больше не используемый deployed asset.
